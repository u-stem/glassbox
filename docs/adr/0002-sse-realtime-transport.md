# 0002: リアルタイム配信に SSE を採用する

## Status

Accepted

## Context

gateway で捕捉した Kafka の内部イベント(produce/consume、リバランス、オフセット変化など)を、ブラウザ上の可視化 UI にほぼリアルタイムで届ける必要がある。配信方式の候補は大きく分けて 2 つある。

1. **WebSocket**: 双方向通信が可能な永続コネクション
2. **Server-Sent Events (SSE)**: サーバーからクライアントへの単方向ストリーム

glassbox のデータフローは「server → client のイベントストリーム」と「client → server のシナリオ実行コマンド」が明確に分離できる形をしている。クライアントからサーバーへの操作(`produce-burst` 等のシナリオ実行)は都度実行される単発のコマンドであり、双方向の常時接続を要求しない。

また、ブラウザのタブ再読み込みやネットワーク瞬断からの復帰時に、イベントを欠落なく(または欠落を検知した上で)再開できる必要がある。

## Decision

- **配信方式は SSE を採用する。** client → server のコマンドは通常の HTTP POST(`POST /api/themes/kafka/scenarios/:scenarioId` 等)で行い、WebSocket は使わない。
  - 理由: 本ユースケースは単方向ストリームで要件を満たせる。SSE はブラウザの `EventSource` に**自動再接続**が組み込まれており、`Last-Event-ID` ヘッダーによる再開の仕組みも標準化されている。WebSocket を採用する場合、再接続・再開ロジックを自前で実装する必要があり、単方向要件に対しては過剰な複雑さになる。
  - 双方向のリアルタイム通信(例: サーバーからのプッシュ通知に対する即時応答)が実在の要件として出てきた場合は、その時点で WebSocket への移行を再検討する。

- **gateway は in-memory のリングバッファに直近イベントを `seq`(単調増加する連番)付きで保持する。** SSE クライアントは再接続時に `Last-Event-ID`(= 最後に受信した `seq`)を送り、gateway はそれ以降のイベントをリングバッファから再送して追い付かせる。

- **ギャップ検出**: 再開要求された `seq` がリングバッファに保持されている最古の `seq` より古い場合(= バッファ溢れで該当イベントが失われている場合)、部分的な再送は行わない。代わりに「reset 指示 + 現在の world snapshot」を送信し、クライアント側の状態を丸ごと作り直させる。半端に欠落したイベント列を再送すると、クライアントの状態が永久に発散したまま気づけなくなるリスクがあるため、欠落を検知したら潔く全体を再同期する方針とする。

- gateway は `admin.snapshot` イベントを定期的に送出する。このイベントは SSE のギャップ復旧アンカーとしてだけでなく、権威モデル(ADR-0003)における authoritative baseline としても機能する。resync の仕組みと状態の権威モデルを別々に設計せず、同じ snapshot の仕組みに統合する。

- **`EventTransport` のような抽象インターフェースは作らない(YAGNI)。** 現時点で SSE 以外のトランスポートに切り替える具体的な要求はなく、抽象化のコストが将来の利益を上回る。WebSocket が必要になった時点で、その時の要件を見てから設計する。

## Consequences

- ブラウザの `EventSource` は任意ヘッダーを付与できないため、`Last-Event-ID` は `EventSource` が自動再接続時に送信する標準ヘッダーの挙動に依存する。手動での再接続コード(fetch ベースの SSE 実装)を書く場合は、このヘッダー送出を自前で行う必要がある。
- リングバッファのサイズは「どれだけの時間・イベント数の瞬断まで無停止で復旧できるか」を決めるパラメータになる。サイズが小さすぎるとギャップ検出(= 全体 reset)が頻発し、UI 側の体験が悪化する。Phase 1 以降で実運用のイベント量を見ながら調整する。
- gateway プロセスの再起動時は in-memory バッファが失われるため、全クライアントがギャップ検出 → snapshot reset を経由することになる。これは許容する(gateway はステートレスな再起動を前提とした設計方針のため)。
- 双方向通信が必要になった場合(例: クライアント側からの細かいインタラクティブ操作をリアルタイムに反映したい等)は、本 ADR を再検討し WebSocket への移行を別途決定する。
